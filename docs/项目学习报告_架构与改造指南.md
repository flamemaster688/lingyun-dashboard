# 灵运 BI 看板 · 项目学习报告（架构、部署、数据与改造指南）

> 适用对象：纯小白 / 刚接手项目的人
> 目标：用大白话讲清「这项目是什么、怎么搭的、数据从哪来、怎么改」，让你照着能学、照着能改。

---

## 0. 一句话先看懂

这是一个**纯前端静态网站**的「数据看板」（BI = Business Intelligence，商业智能，说白了就是"把数据画成图表的网页"）。

- **没有后端**（没有服务器在后台跑程序），**没有数据库**（没有 MySQL 那种存数据的软件）。
- 所有数据被打成一个 **27MB 的 `data.js` 文件**，跟着网页一起下载到每个人的浏览器里。
- 打开方式：双击 `static/index.html`，或者部署到 GitHub Pages 后拿到一个公网链接发给别人。
- 三个人分工，每人负责几个页面文件，**最后用一条命令把大家的文件合并打包成一个发布版**。

---

## 1. 有没有前后端？用什么框架？

### 前端（你看到的网页）
- **原生 HTML + CSS + JavaScript**，没有用 React、Vue 这类"前端框架"（所以代码读起来就是普通的网页三件套，对小白反而友好）。
- **图表库：ECharts**（百度开源的画图工具，柱状图/饼图/地图都是它画的）。
- **Excel 处理：SheetJS（xlsx）**（用来导入 Excel 数据）。
- 项目自己写了一个**极简"内核框架"**，挂在全局变量 `window.LY` 上，负责三件事：① 页面注册 ② 导航切换 ③ 统一数据接口 + 筛选计算。

### 后端（后台程序）
- **没有。** 没有任何需要 7×24 小时运行的服务器程序。
- 你可能会看到 `app.py`、`wps_connector.py`、`kdocs_to_csv.py` 等 Python 文件 —— 它们**不是网站运行需要的后端**，而是"取数工具"，只在**刷新数据时本地跑一次**，把线上表格的数据拉下来、转成数据文件。平时网站打开根本不碰它们。

### 小结
> 这套东西的定位 = **"把一份数据文件，渲染成好看图表的纯网页"**。简单、好部署、不花钱，但代价是"数据全发给每个人看"（所以你之前要的密码保护才重要）。

---

## 2. 有没有数据库？

**没有传统数据库。** 但有"数据"，只是存在另一种形式：

- 项目的"数据库"就是 `static/data.js` 里的一个**大 JSON 对象** `window.LINGYUN_DATA`。
- 它相当于一个**"内置在网页里的只读数据库"**：网页一打开就把这 27MB 读进内存，然后所有图表/表格都从这里面取数。
- 结构大致是这样（顶层叫"域 domain"，每个域是一块数据）：

| 域（键名） | 是什么 | 体量 |
|---|---|---|
| `meta` | 元信息（数据来源、月份、省份列表） | 小 |
| `overview` | 数据总览页用 | 对象 |
| `agentMonthly` | **智能体按月×省明细**（我们重点改的） | **31850 行** |
| `agents` | 智能体清单 | 113 条 |
| `provinces` | 省份分析 | 33 条 |
| `tracking` | 平台埋点分析 | 143 条 |
| `capability` | 能力标签 | 对象 |
| `agentCaseCatalog` | 案例清单 | 174 条 |
| … | 其他 | — |

**优缺点（小白重点记）：**
- ✅ 优点：打开即用，不用连服务器、不用配数据库。
- ❌ 缺点：数据**全量下发给每个访客**。也就是说任何人打开网页，都能在浏览器里把这份 27MB 内部数据下载走 —— 这正是"为什么要做密码保护"的根本原因。

## 3. 项目目录结构（你该认识的几个文件夹）

```

│   ├── core/            内核框架（重点理解）
│   │   ├── core.js         导航切换 + 筛选计算 + 页面调度
│   │   └── data.js        统一数据接口（页面只通过它读数据）
│   ├── pages/          各页面（每人负责自己的文件）
│   │   ├── overview.js     数据总览
│   │   ├── agents.js       智能体（我们这次大改的）
│   │   ├── province.js     省份分析
│   │   ├── tracking.js     平台分析
│   │   ├── quality.js      质效分析
│   │   ├── alarms.js       告警中心
│   │   └── report.js       报告生成
│   ├── data.js          👉 "数据库"（自动生成，千万别手改！）
│   └── vendor/         第三方库（echarts、xlsx、中国地图）
│
├── build/           👉 构建 & 数据处理脚本（python/node）
│   ├── fetch-data.py     统一取数：把各页数据源合并成 data.js
│   ├── gen_preview_data_v2.py  生成智能体域（从 CSV）
│   ├── merge_agents_v2.js      把智能体域并入 data.js
│   ├── bundle.js         👉 打包：把 core+所有 pages 合成一个文件
│   └── ...（其它一次性/调试脚本）

│   └── style.v6.css
```

**一句话记牢：**
- 写代码改 **`static/`**。
- 发布上线用的是 **`dist/`**（由 `static/` 自动生成）。
- 数据来自 **`static/data.js`**（由 `build/` 里的脚本生成）。

## 4. 数据是怎么关联起来的？（核心逻辑）

这是整个项目最关键的一条链路，画成图就是：

```
金山文档(在线表格)
      │  （赵莹用 kdocs 连接器把各页数据拉下来）
      ▼
build/sources/<页面id>.json   （每页一份中间数据）
      │  （python fetch-data.py merge 合并）
      ▼
static/data.js  =  window.LINGYUN_DATA  （"内置数据库"）
      │
      ▼
core/data.js  （统一数据接口 window.LY.data）
      │  （页面只读这里，不直接碰 data.js）
      ▼
pages/<id>.js  （各页面取数 → 画图表 / 填表格）
```

**关于智能体域（你这次重点接触的部分）：**
- 智能体的明细（`agentMonthly` 那 3 万多行）是由 `build/gen_preview_data_v2.py` 从**原始 CSV 文件**（`_raw_month_05.csv` ~ `_raw_month_08.csv` 等）算出来的。
- 然后 `build/merge_agents_v2.js` 把它并入 `data.js`。
- 我们这次新增"节约金额 / 产生真实价值"等字段，用的是 `build/extract_province_list.py`（抽取）+ `build/merge_province_list.js`（合并）这套同样的思路。

**页面怎么"安全"地读数据（重要约定）：**
> 页面代码**只通过 `window.LY.data` 读数据**，绝不直接读 `window.LINGYUN_DATA`，也绝不在页面里自己连金山文档。
> 这样做的好处：哪天数据源从金山文档换成别的，只要改 `core/data.js` 一处，所有页面都不用动。

## 5. 页面是怎么组织和渲染的？

1. 每个页面文件最后都会调用一句：
   ```javascript
   window.registerPage({ id: "agents", render: function(){ ... } });
   ```
   相当于"我这个页面叫 agents，渲染函数长这样，先报到内核去"。
2. `core/core.js` 负责：左边点导航 → 切换 tab → 找到对应页面 → 调用它的 `render()`。
3. `render()` 里干两件事：
   - 用 `window.LY.data.xxx()` 取数据；
   - 用 `innerHTML` 写 HTML（卡片/表格）+ 用 ECharts 画图表。
4. **筛选**（比如选月份、选省份）：由 `core.js` 统一算好一个"已过滤的视图"，页面直接拿过滤后的结果画，不用每个页面自己写筛选逻辑。

## 6. 任务怎么分配的？（三人协作）

项目是按"**页面物理隔离**"设计的：每个人只改自己名下的 `pages/<id>.js`，几乎不会互相冲突。

| 负责人 | 负责页面文件 | 页面内容 |
|---|---|---|
| **吴超** | `overview.js` | 数据总览 |
| | `province.js` | 省份分析 |
| | `report.js` | 报告生成 |
| **羽琪** | `agents.js` | 智能体（我们这次大改的就是它） |
| | `alarms.js` | 告警中心 |
| **赵莹** | `tracking.js` / `tracking-monthly.js` | 平台分析（埋点） |
| | `quality.js` | 质效分析 |
| | `core/*`、`style.v6.css`、`index.html` | 内核 / 配色 / 导航 / 数据管线 |
| | 数据刷新 + 合并打包 + 发布 | 总协调 |

**协作流程（记住这条主线）：**
1. 三人各自 `git clone` 同一仓库，在**自己的 `pages/<id>.js`** 上改。
2. 本地自检：`node build/check.js`。
3. 提交：`git add 自己的文件 && git commit && git push`。
4. **赵莹**负责 `pull` 合并 → `node build/bundle.js`（打包）→ 推 `main` → 部署。
5. 数据刷新：赵莹跑取数脚本重写 `data.js` 后重新部署。

## 7. 怎么部署？（让别人也能打开）

### 方式 A：本地自己看（最简单）
```bash
# 直接双击
open static/index.html

# 或起个本地小服务器（推荐，避免个别浏览器限制）
cd static && python3 -m http.server 8080
# 浏览器开 http://localhost:8080
```

### 方式 B：打包成发布版（改完代码后必做）
```bash
node build/bundle.js
```
这一条命令会把 `core/` + 所有 `pages/*.js` 合并成 `dist/lingyun.bundle.js`，并生成 `dist/index.html`。**线上跑的是 `dist/`，不是 `static/`**。

### 方式 C：发公网链接（发给同事/外部）
**首选 GitHub Pages（免费、无额度上限）：**
- 把仓库 push 到 GitHub（`main` 分支），配好 `.github/workflows/deploy.yml`，push 即自动部署；
- 或者把 `dist/` 推到 `gh-pages` 分支，仓库 Settings → Pages 指向它；
- 最终链接形如：`https://<用户名>.github.io/lingyun-dashboard/`。

**备选：** CloudStudio / Vercel / Cloudflare Pages，直接把 `dist/` 拖上去（静态站点）。
> 注：Netlify 之前账号额度用尽、且旧 Token 已泄露，已废弃不用。

### ⚠️ 部署最关键的一条铁律
> **改了 `static/` 一定要重跑 `node build/bundle.js` 再部署**，否则线上（`dist/`）永远看不到你的改动。这是新人最容易踩的坑。

## 8. 改数据 / 改样式，到底改哪里？（重点，学代码从这里入手）

### 🎨 改「样式 / 外观」
| 你想改什么 | 改哪个文件 |
|---|---|
| 全局配色、字体、卡片/表格长相 | `static/style.v6.css` |
| 导航栏、页面骨架、区块布局 | `static/index.html` |
| 某个页面内部的小卡片/表格样式 | 对应 `static/pages/<id>.js` 里写的 HTML 字符串（配合 css 的 class） |

改完 → `node build/bundle.js` → 部署。

### 📊 改「数据」
分两种情况：

**情况 A：数据内容变了（比如某月数字更新）**
- 线上数据源在**金山文档**。赵莹跑取数脚本重生成 `data.js` 即可，**页面代码一行都不用动**。
- 如果你只是本地想换数据：改 `build/sources/*.json` 或原始 CSV，再重跑对应的生成脚本 → 生成新的 `data.js`。

**情况 B：想加一个新指标 / 新字段（进阶）**
1. 在**数据生成脚本**（`build/*.py` 或 `build/*.js`）里把新字段算出来，写进 `data.js` 的对应域；
2. 如果是**新的顶层域**，要在 `core/data.js` 的 `PAGE_DOMAINS` 里登记，让页面能取到；
3. 在对应 `pages/<id>.js` 里：在**列注册表**加字段 → 在 `render` 里显示它 → 必要时在筛选/口径里处理；
4. 重跑 `bundle` + 部署。

> 💡 真实教训：我们这次加"节约金额 / 产生真实价值"字段，就是因为漏了一步——`normalizeRow` 没把新字段映射进规范化行，导致表格显示为空。这就是典型的"数据关联没接好"的坑。

### 📈 改「图表 / 计算逻辑」
- 图表样式/类型/配色都在 `pages/<id>.js` 里的 ECharts `option` 对象，改这里；
- KPI 数值、正向率等计算也在 `pages/<id>.js`（或 `build/` 生成脚本）里。

## 9. 给你的学习路线建议（循序渐进）

1. **先看效果**：双击 `static/index.html` 打开，建立"页面长什么样"的印象。
2. **读骨架**：读 `static/index.html`（看导航和容器），再读 `core/core.js`（看导航怎么切换、页面怎么被调用）。
3. **读数据接口**：读 `core/data.js`（就 70 行，看懂"页面只通过 LY.data 取数"这条约定）。
4. **读一个页面**：挑你关心的（比如 `agents.js`），看它怎么 `registerPage` + `render` + 用 `LY.data` 取数 + 画 ECharts。
5. **动手闭环**：改一行 `style.v6.css` → 跑 `node build/bundle.js` → 看 `dist/index.html` 变化。建立"改 → 打包 → 看"的肌肉记忆。
6. **再看数据脚本**：读 `build/fetch-data.py`、`gen_preview_data_v2.py`，理解 `data.js` 是怎么从表格变出来的。

---

## 10. 新手必知的 4 个坑

1. **改了 `static/` 但没重跑 `bundle.js`** → 线上永远看不到改动。（最高频！）
2. **手改 `data.js`** → 它是自动生成的，下次一跑脚本就被覆盖。改数据走取数脚本。
3. **页面里直接读 `window.LINGYUN_DATA`** → 破坏统一接口约定，以后换数据源会全员返工。一律走 `window.LY.data`。
4. **以为有后端/数据库** → 其实没有。所有数据都在客户端，敏感数据务必加密码保护（即上一轮聊的密码方案）。
